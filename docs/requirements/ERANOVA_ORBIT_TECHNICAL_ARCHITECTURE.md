# ERANOVA ORBIT — Final Technical Architecture
**Version:** 1.0  
**Status:** Architecture baseline  
**Product identity:** One company. One command centre.  
**AI assistant:** NOVA

## 1. Executive architecture decision

Eranova Orbit is a web-first company operating system with two connected surfaces:

1. **Public marketplace:** presents Eranova products, captures enquiries and demos, publishes product information and routes prospects into the CRM.
2. **Private command centre:** gives authorized staff a unified view of products, customers, projects, tasks, employees, campaigns, analytics, support and management reporting. NOVA provides conversational and voice-enabled assistance over permitted company data and actions.

Orbit is the central management layer; it is not a forced rewrite or merger of the products it manages. Each product retains its own repository, deployment lifecycle, data store and domain logic. Orbit integrates with them through documented, authenticated APIs and provider connectors.

## 2. Confirmed infrastructure decisions

| Area | Decision |
|---|---|
| Repositories | Each product has its own repository |
| Hosting | Vercel for frontend/public web; Render for backend services |
| Integration strategy | Progressive API integrations, beginning with highest-value connections |
| AI | Configurable provider/model adapter; avoid provider lock-in |
| Orbit database | Dedicated PostgreSQL database |
| Product databases | Remain independently owned; access through secure APIs/connectors |
| Growth | Product registry and reusable integration framework support future products |
| Initial products | ShulePoa, HostPilot, OTPGuard, SitePoa, MenuPoa |

## 4. Application architecture

### 4.1 Frontend

- React + Vite, JavaScript/JSX.
- Tailwind CSS and a consistent component system (shadcn/ui where appropriate).
- React Router for route structure.
- TanStack Query or an equivalent server-state library for API caching, invalidation and loading/error states.
- React Hook Form plus schema validation (for example Zod) for complex forms.
- Recharts for dashboards and reports.
- Accessible charts, tables, keyboard navigation, responsive navigation and reduced-motion support.
- Public marketplace and private command centre may share a design system, tokens and reusable components while keeping route groups and authorization boundaries distinct.
- Vercel deployments should use separate preview and production environments. Protect private routes at both the UI and API layers; hiding a menu item is not authorization.

Suggested route groups:
- `/` — public marketplace
- `/products/:slug` — public product detail
- `/solutions`, `/pricing`, `/resources`, `/careers`, `/contact`
- `/login`, `/forgot-password`
- `/app/*` — authenticated command centre
- `/app/nova` — NOVA workspace

### 4.2 Backend

- Python + FastAPI, deployed on Render.
- Modular monolith initially: separate domain modules, schemas, services and repositories within one deployable API.
- SQLAlchemy 2.x for persistence; Alembic for migrations.
- Pydantic for request/response validation.
- OpenAPI documentation generated by FastAPI.
- Background processing for scheduled reports, analytics ingestion, notifications, webhook processing and long-running AI jobs. Use a managed queue/worker pattern when needed; do not rely on in-process background tasks for durable work.
- WebSockets or server-sent events only where real-time interaction is required (NOVA streaming, notifications, live status).
- Version APIs under `/api/v1`.
- Keep business rules in services, not route handlers or frontend components.

Recommended backend modules:
`identity`, `authorization`, `company`, `products`, `integrations`, `crm`, `customers`, `projects`, `tasks`, `people`, `attendance`, `marketing`, `analytics`, `monitoring`, `nova`, `approvals`, `finance`, `support`, `documents`, `meetings`, `notifications`, `reports`, `audit`.

### 4.3 Database

Orbit uses a dedicated PostgreSQL database. Product databases are not merged into it.

Design rules:
- UUID or another stable non-guessable identifier for primary keys.
- Every company-owned record is scoped by `company_id` where multi-company support may eventually be required; initially enforce Eranova tenancy.
- Every product-specific record references `product_id`.
- Foreign keys, unique constraints, indexes and transaction boundaries must be deliberate.
- Use migrations for all schema changes.
- Use PostgreSQL row-level security where useful as defense in depth, while retaining application-level authorization.
- Store timestamps in UTC; display in the user's configured timezone.
- Use soft deletion only where justified, with explicit retention and recovery rules; never silently erase financial or audit history.
- Keep analytics aggregates separate from unnecessary personal/customer data.
- Backups, restore testing, retention and access controls are release requirements.

Conceptual entity groups:
- Identity: `users`, `employees`, `departments`, `roles`, `permissions`, `role_permissions`, `user_roles`, `sessions`.
- Products: `products`, `product_members`, `product_pricing`, `product_status_history`, `product_integrations`.
- Integrations: `integration_connections`, `integration_credentials` (secret references only), `webhook_endpoints`, `webhook_events`, `sync_runs`, `sync_cursors`.
- CRM: `leads`, `lead_sources`, `customers`, `contacts`, `opportunities`, `activities`, `follow_ups`, `pipelines`, `pipeline_stages`.
- Work: `projects`, `project_members`, `tasks`, `subtasks`, `milestones`, `task_dependencies`, `submissions`, `reviews`, `comments`.
- People: `employee_profiles`, `attendance_records`, `leave_requests`, `performance_observations`.
- Marketing: `campaigns`, `campaign_assets`, `content_items`, `publishing_jobs`, `campaign_metrics`.
- Analytics: `tracked_websites`, `tracking_events`, `analytics_sources`, `metric_snapshots`, `monitoring_checks`.
- NOVA: `conversations`, `messages`, `agent_tool_definitions`, `tool_executions`, `approval_requests`, `knowledge_sources`, `knowledge_chunks`.
- Finance: `invoices`, `expenses`, `payments`, `subscriptions`, `commissions` (only as needed and with appropriate controls).
- Support: `support_tickets`, `ticket_messages`, `ticket_events`.
- Documents/meetings: `documents`, `document_permissions`, `meetings`, `meeting_attendees`, `meeting_minutes`, `action_items`.
- Platform: `notifications`, `audit_logs`, `report_jobs`, `export_jobs`.

This is a domain model, not a mandate to create every table in the first sprint. Implement schema incrementally with each module.

## 5. Product integration architecture

### 5.1 Product registry

A product is registered in Orbit with:
- Name, slug, description, category, logo, public website and status.
- Product owner/manager and authorized team members.
- Repository URL and deployment/project references.
- Integration capabilities and connection status.
- Analytics source/tracking identifier.
- Pricing/plan metadata, launch date and support contact.
- Optional links to product-specific documentation and status page.

Adding a product should be primarily configuration plus an adapter/API connection, not a redesign of Orbit's core schema.

### 5.2 Adapter contract

Create a common integration interface with capabilities such as:
- `health_check()`
- `get_product_metadata()`
- `get_usage_metrics(range, dimensions)`
- `get_customer_summary(filters)` (only if the product API permits it)
- `receive_webhook(event)`
- `sync_incremental(cursor)`
- `get_service_status()`

Not every product must implement every capability. Store supported capabilities and version per connection. Use explicit adapters for differences between product APIs; do not pretend all product databases have identical schemas.

### 5.3 Integration security and reliability

- Prefer service-to-service OAuth/client credentials or scoped API keys with rotation.
- Keep secrets in Render environment secrets or a dedicated secret manager; store only references/metadata in Orbit DB.
- Never expose product API secrets to browser code, logs, NOVA prompts or client-side bundles.
- Require TLS, request signing where supported, replay protection, timestamps and idempotency keys for webhooks.
- Verify webhook signatures before processing.
- Use retries with exponential backoff, dead-letter handling and visible sync status.
- Track last successful sync, freshness, errors and integration version.
- Apply least-privilege scopes per integration and per product.
- Use read-only access by default. Add write capabilities only when the product has an approved use case.
- Never directly query a product's database from the browser. Prefer its API. A private network/database connector is an exceptional, narrowly scoped server-side option.
- Do not copy all product customer records into Orbit by default. Sync only the minimum fields needed for CRM, reporting or operations, with documented ownership and retention.

### 5.4 Progressive rollout order

1. **Foundation:** product registry, integration connection records, API key/secret management, webhook receiver, integration health dashboard.
2. **GitHub + Vercel:** repositories, issues/PR metadata, commit/PR links to tasks, deployment status and build outcomes.
3. **Website analytics:** GA4/Search Console connectors where available; otherwise Orbit-owned privacy-conscious tracking SDK for owned websites.
4. **Lead capture:** marketplace forms and selected product contact/demo events into Orbit CRM.
5. **Product APIs:** integrate each product in order of operational value and API readiness; start with read-only status and aggregate metrics.
6. **Support/subscriptions/finance:** only where authoritative product/payment APIs exist and access has been approved.
7. Add new products through the same registry and adapter contract.

## 6. Authentication, roles and permissions

Support custom roles and granular permissions. Each employee has one primary department but can belong to multiple product and project teams.

Suggested starter roles (all customizable):
- Super Admin / Company Owner
- Executive
- Department Manager
- Product Manager
- Project Manager
- Developer
- Sales
- Marketing
- HR
- Finance
- Support
- Employee / Intern
- Read-only Auditor

Authorization dimensions:
- Action: `read`, `create`, `update`, `delete`, `approve`, `export`, `manage`.
- Resource: product, lead, customer, project, task, employee, campaign, invoice, ticket, document, integration, report.
- Scope: company, department, assigned product, assigned project, own records.
- Context: sensitivity, status, approval state and data ownership.

Every API endpoint and every NOVA tool must check permissions server-side. UI restrictions are convenience only. Log role/permission changes and privileged access.

## 7. NOVA AI architecture

### 7.1 Provider-independent design

Build an internal AI gateway interface so application code never depends directly on one model provider. Provider adapters should normalize:
- Chat completion / streaming.
- Tool/function calling.
- Structured JSON output.
- Model capabilities and context limits.
- Usage, latency and cost metadata.
- Provider errors and retry rules.

Configuration should select provider, model, endpoint, API key reference, temperature/limits and feature availability per environment. Support a provider change through configuration and adapter implementation, not a rewrite of NOVA's business logic. Do not promise that every model supports every tool/voice feature; capability-check at runtime.

### 7.2 NOVA request lifecycle

1. Authenticate the user and load permitted context.
2. Classify request and determine whether it needs retrieval, a tool, or a direct answer.
3. Retrieve only relevant authorized records.
4. Send a bounded context and allowed tool schemas to the configured model.
5. Validate proposed tool arguments against schemas and policy.
6. Enforce permissions and approval policy on the backend.
7. Execute permitted operations with idempotency and audit logging.
8. Return a result with links/record IDs and distinguish completed actions from recommendations.
9. Save conversation and tool-execution metadata according to retention policy.

### 7.3 Tool authority

- **Read:** retrieve/search permitted company data, summarize and report.
- **Execute:** create/update ordinary permitted tasks, draft content, assign work within authority, create CRM follow-ups and generate reports.
- **Approval required:** financial transfers/payments, issuing refunds, deleting critical records, changing roles/permissions, employee termination or other high-impact HR decisions, publishing high-impact external communications, changing security settings and other sensitive actions.

Approval must be tied to the exact action, target and parameters. If parameters change, obtain a new approval. Never let the model approve its own action. The backend must independently enforce policy even if the model asks to bypass it.

NOVA may prepare HR performance summaries but must not make autonomous hiring, firing, promotion or disciplinary decisions. It must distinguish source facts from estimates and recommendations.

### 7.4 Voice

- Push-to-talk as the safe default.
- Explicit microphone permission and clear recording/listening indicator.
- Speech-to-text, transcript review, text-to-speech and interruption support.
- Voice requests follow the same authentication, permission, approval and audit path as typed requests.
- Do not execute consequential actions solely from an ambiguous transcript; show the interpreted action and obtain confirmation/approval.
- Provide a text fallback when browser/device speech features are unavailable.

### 7.5 Knowledge and memory

Use retrieval over authorized company records and documents. Do not put the entire database into a prompt. Separate company facts, source documents, current conversation context and user preferences. Apply source permissions before retrieval and again before returning results. Show source records for important business claims. Support correction of stale knowledge and source freshness metadata.

## 8. Core business modules

### Public marketplace
Product catalogue, product detail pages, search/filter, pricing, demos, resources, careers, contact, lead capture and CMS. All submissions create traceable CRM records with source attribution and consent metadata where required.

### Executive overview
Real-time or clearly timestamped summaries of products, projects, leads, customers, tasks, sales, traffic and service health. Never display seeded/demo values as live company metrics.

### CRM and customers
Configurable sales pipeline; lead ownership and follow-ups; customer profiles and interaction history; lead conversion preserving history; NOVA prioritization and draft assistance.

### Projects and tasks
Projects linked to products; task assignment, milestones, dependencies, deadlines, comments, attachments, submissions and review workflow. GitHub references link to tasks, but commits alone do not prove completion. Human review remains part of acceptance.

### People operations
Employee profiles, departments, role access, schedules, attendance, leave and transparent performance observations. Attendance tracking must be disclosed and proportionate; no covert monitoring.

### Marketing
Campaign planning, content drafts, assets, calendars and connected publishing workflows. Clearly distinguish draft, scheduled, published and failed states. Do not claim social publishing is available until the relevant account integration is connected and tested.

### Analytics and monitoring
Website traffic, sources, top pages, conversions and aggregate device/geographic trends. Technical monitoring (uptime, HTTP/API health, SSL/domain expiry where supported) must be separate from marketing analytics. Display source and last-updated time.

### Finance and subscriptions
Begin with management reporting and records that can be verified from connected sources. Clearly distinguish invoices, payments, outstanding balances, expenses, revenue and subscription status. Do not represent a management dashboard as a complete accounting system or initiate payments without a separate authorized workflow.

### Support
Product-linked tickets, assignment, status, response history, resolution and service metrics. NOVA may summarize and draft responses but human staff remain accountable.

### Reports and documents
Role-scoped reports with date range, source, freshness and export. Document centre uses document-level permissions and audit history.

## 9. Security, privacy and compliance

- Apply the Kenya Data Protection Act and other applicable requirements; obtain legal/privacy review before production processing.
- Define purpose, lawful basis, notices, consent where applicable, retention and data-subject request processes.
- Minimize collection of personal data; do not use sensitive employee/customer information as general analytics dimensions.
- Encrypt traffic in transit and sensitive data at rest; hash passwords using a modern password hashing algorithm.
- Use secure, HttpOnly, SameSite cookies or a carefully designed token/session architecture; protect against CSRF, XSS, injection and session fixation.
- Enforce MFA for privileged accounts where feasible.
- Rate-limit authentication, public forms, AI endpoints and expensive reports.
- Validate uploads, scan files where possible, limit file size/type and use private object storage.
- Redact secrets and sensitive fields from logs.
- Maintain immutable or append-only audit events for privileged actions, approvals, integration changes and data exports.
- Establish backup, restore, incident response and vulnerability management procedures.
- Treat external web pages, uploaded files and product data as untrusted input. Prompt injection in retrieved content must not grant tools or permissions.

## 10. Deployment and environments

### Environments
- Local development.
- Preview/staging.
- Production.

Use separate databases, credentials, AI keys and integration credentials per environment. Never point preview deployments at production data by default.

### Vercel
- Frontend deployment with preview URLs and protected production branches.
- Environment variables only for public configuration; no server secrets in `VITE_*` variables.
- Configure domain, HTTPS, security headers and caching intentionally.

### Render
- FastAPI web service.
- Background worker and scheduler as separate services when durable asynchronous workloads are introduced.
- Managed PostgreSQL or approved PostgreSQL hosting for Orbit.
- Health/readiness endpoints, structured logs and deploy rollback.
- Keep secrets in platform secret configuration.

### CI/CD
- Pull-request checks: formatting/lint, type/schema checks where applicable, unit tests, integration tests and dependency/security scans.
- Build and test before deployment.
- Apply Alembic migrations as a controlled release step with backup/rollback planning.
- Smoke-test health, auth, database connectivity and critical user journeys after deployment.
- Use feature flags for incomplete integrations.

## 11. Scalability and extensibility

Scale in stages:
1. Modular monolith + managed PostgreSQL + background worker.
2. Add indexes, caching, connection pooling, pagination, query monitoring and job queues as demand grows.
3. Separate high-load modules (analytics ingestion, notifications, AI orchestration) into services only when justified.
4. Add read replicas/partitioning/warehouse architecture only when metrics demonstrate need.
5. Support product onboarding through registry + adapter + capability metadata + permission scopes.

Design for horizontal stateless API scaling. Store durable state in PostgreSQL/object storage/queue, not process memory. Use idempotent jobs, bounded retries, backpressure and rate limits. Establish measurable service objectives before optimizing.

## 12. Observability and operational readiness

Track:
- API latency/error rate, database health and connection pool use.
- Job queue depth, retries and failed jobs.
- Integration freshness, failures and webhook processing.
- NOVA latency, provider errors, token/cost usage and tool outcomes.
- Product uptime/deployment health.
- Security events, approvals and audit trail.

Provide correlation IDs across frontend, API, workers and integration calls. Alerts should be actionable and avoid exposing sensitive data.

## 13. Delivery phases

**Phase 0 — Discovery and foundation**
Repository review, product API inventory, data ownership map, security model, design system, environments, authentication, PostgreSQL and audit foundation.

**Phase 1 — Core Orbit**
Product registry, users/roles/permissions, executive shell/dashboard, global search foundation, notifications and settings.

**Phase 2 — Public marketplace**
Product pages, CMS basics, enquiry/demo forms, consent/source attribution and CRM lead creation.

**Phase 3 — Company operations**
CRM, customer records, projects, tasks, reviews, employee portal and department/product scopes.

**Phase 4 — First integrations**
GitHub, Vercel, website analytics and monitoring; add product APIs progressively according to value and readiness.

**Phase 5 — Marketing, support and reporting**
Campaigns, content workflows, support tickets, exports and scheduled reports.

**Phase 6 — NOVA**
Provider gateway, authorized retrieval, tool registry, approvals, action history, voice and cost controls.

**Phase 7 — Finance and subscriptions**
Verified source integrations, financial management reporting and subscription visibility.

**Phase 8 — Production hardening**
Security review, privacy review, load testing, backup/restore exercise, accessibility, incident runbooks and operational acceptance.

## 14. Definition of done

A feature is not complete merely because a screen exists. It is complete when:
- UI is connected to a real backend workflow.
- Data persists and is validated.
- Authorization is enforced on the server.
- Loading, empty, success and error states work.
- Audit events exist for sensitive actions.
- Tests cover critical behavior and permission boundaries.
- Integration failures are visible and recoverable.
- Documentation and environment configuration are updated.
- No placeholder button or fabricated metric is presented as functional/live.

## 15. Architecture decisions to revisit with evidence

The following remain implementation choices, not reasons to block the foundation:
- Whether to use a managed queue such as Redis-backed jobs or a cloud task service.
- Whether to introduce a separate analytics warehouse.
- Whether to split the modular monolith into services.
- Which speech and AI providers to enable in each environment.
- Exact product API scopes and sync frequency.
- Whether Orbit eventually supports multiple legal entities/tenants.

Record each material decision in an Architecture Decision Record (ADR) with context, options, decision and consequences.
